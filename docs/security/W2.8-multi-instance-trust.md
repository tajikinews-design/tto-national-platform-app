# W2.8 — multi-instance signed-trust synchronization (synthetic only)

Baseline: W2.7 Draft PR #77 exact HEAD `b15c7ea980254f8cba7e9f10bea88187547f9e4e`. This branch is stacked on that commit; no merge, deployment, Docker, SQL, financial transaction, production route, or live permission.

## Security decision
W2.7's local signed trust snapshot is not a globally fresh revocation guarantee. W2.8 requires a synchronous authority-head confirmation immediately before the sensitive accept boundary. If communication fails, head differs, snapshot expires, root signature is invalid, ordering is broken, or clock regresses: DENY. A finite TTL alone cannot prevent a recently revoked key being accepted by an isolated replica.

## Laboratory contract
- W2.7 exact signature, epoch, chain, role, immutable tombstone, generation and expiry rules remain authoritative.
- `SyntheticTrustAuthority` publishes W2.7-signed snapshots and exposes checkpoint and ordered history from in-memory state; `SyntheticTrustReplica` receives and validates every missed W2.7 snapshot, including its previous hash.
- Local W2.7 check is necessary but insufficient. Every simulated trust decision requires exact authority head match; head changes, inability to reach authority, expired status, wrong role, revoked key or integrity errors block the decision.
- An explicit quarantine state follows synchronization failure/head discrepancy; rejoining requires full validation via `synchronize`.
- `ok:true` is a **simulation-only** trust-check result and always has `canGrantPermission:false`. Operational authorization cannot depend on this mock.

## Assumptions and critical non-claims
This is an in-process, single-threaded fixture. Its synchronous `confirm` models an instantaneous linearizable head read **only within the fixture**, NOT a distributed linearizable protocol. There is no actual interprocess network, quorum, consensus, authority attestation, globally trusted clock, durable anti-rollback anchor, resilient signing service, atomic transaction/commit, or authority failover. A race after confirmation and before an external commit remains unresolved: a real deployment must validate at the actual commit boundary under a linearizable transaction/fencing arrangement, and must specify revocation effective-time semantics.

W2.7 trusted local PDP enrollment remains TOFU-like; W2.8 does not attest executable identity. No route wiring, actual permission, business data, payments or trades. For any production implementation these are release-blocking gaps.
