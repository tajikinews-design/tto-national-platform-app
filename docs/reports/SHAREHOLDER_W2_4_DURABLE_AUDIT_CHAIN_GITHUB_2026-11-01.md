# W2.4 — قرارداد ممیزی امنیتی ماندگار آزمایشگاهی و ردیابی درخواست

**تاریخ:** ۱ نوامبر ۲۰۲۶  
**مرجع پذیرفته‌شده:** W2.3، PR #72، SHA `216f5a4bf99fe6ad1cd4ea42d05b24323b94fbdb`  
**وضعیت:** DRAFT — GitHub Actions / CI Only / بدون Docker / بدون PostgreSQL / بدون منابع عملیاتی  
**حوزه:** امنیت دسترسی سهامدار؛ نه سامانه حسابداری تعاونی و نه فعال‌سازی بازار معاملات.

## مسئله

W1 تا W2.3 کنترل نشست، تعاونی، مالکیت، منابع و PDP/PEP را با داده ساختگی آزمایش کردند؛ اما ثبت مسیر تصمیم صرفاً در حافظه بود. W2.4 برای آزمودن شواهد پس از خاتمه یک فرآیند، یک دفتر رویداد **روی دیسک موقت Runner** ایجاد می‌کند که با تعطیل‌کردن و بازگشایی فرآیند هم قابل بررسی بماند.

**حد تعهد این نسخه:** «ماندگاری قابل بررسی در همان Runner آزمایشگاهی و پس از بازکردن دوباره دفتر»؛ نه «لاگ عملیاتی دائمی»، «بایگانی قانونی» یا «تغییرناپذیری اثبات‌شده در برابر مدیر سیستم».

## معماری و مرزهای داده

```
Synthetic client → Temporary BFF (NextRequest / NextResponse)
                      │ BFF_PREFLIGHT
                      ▼
           Ephemeral Nest/Fastify Test Controller
                      │ NEST_SCOPE
                      ▼
              W2.2 cancellable W1 PDP
                      │ PDP_RESULT
                      ▼
                BFF closed response
                      │ BFF_RESPONSE
                      ▼
           W2.4 synthetic append-only journal
                [events.ndjson] + [checkpoint.json] + [writer.lock]
```

منبع داده‌ای در این زنجیره وجود ندارد و **شمارنده مراجعه به منبع صفر** است. هیچ `Route` واقعی یا `Nest AppModule` از W2.4 استفاده نمی‌کند.

### ۱. ساختار یک رویداد

هر رویداد تنها ۹ فیلد مجاز دارد: `schemaVersion`، `sequence`، `requestId`، `phase`، `decision`، `reasonCode`، `at`، `prevHash` و `hash`. مقدار `requestId` یک UUID مصنوعیِ سروری است که زنجیره BFF/Nest/PDP را بدون ذخیره شناسه واقعی سهامدار به هم مرتبط می‌کند. فیلدهای مرحله و دلیل فقط از فهرست محدود و ثابت پذیرفته می‌شوند.

**مواردی که نباید ثبت شوند:** نام/شماره همراه/ایمیل/شناسه ملی یا شناسه Party، کوکی یا توکن نشست، رمز، نقش کاربر، شناسه تعاونی و مالک، Authorization، payload درخواست، پاسخ خام PDP، رکورد سهام، مانده دارایی و اطلاعات پرداخت.

### ۲. ماندگاری و تمامیت

- هر رکورد با `SHA-256(previousHash + newline + canonical event JSON)` به رکورد قبلی متصل می‌شود؛ نقطه آغاز زنجیره ۶۴ صفر است.
- رویداد در فایل `events.ndjson` الحاق می‌شود و `fsync` می‌گیرد؛ سپس `checkpoint.json` با فایل موقت و `fsync` و تغییرنام اتمیک به‌روزرسانی می‌شود و دایرکتوری هم `fsync` می‌شود.
- فایل `writer.lock` فقط با ایجاد انحصاری `wx` گرفته می‌شود؛ writer دوم نمی‌تواند هم‌زمان شروع کند.
- در صورت شکست نوشتن، mismatch بین دفتر و checkpoint، دستکاری یک فایل، حذف رکورد پایانی، داده ناقص یا Symlink غیرمجاز، writer به وضعیت **fail-closed** می‌رود و خودکار چیزی را «اصلاح» نمی‌کند.
- فرایند جدید پس از بسته‌شدن صحیح قبلی، دفتر را می‌خواند و تطابق تمام رکوردها، ترتیب و checkpoint را پیش از پذیرش ادامه کار کنترل می‌کند.

**محدودیت مهم امنیتی:** SHA-256 بدون امضای مستقل یا نقطه اعتماد خارج از دسترس اپلیکیشن، از بازنویسی هم‌زمان دفتر و checkpoint توسط شخصی با دسترسی کامل جلوگیری نمی‌کند. این نسخه تعهدِ عدم انکار یا WORM ندارد. هیچ بایگانی، ذخیره ابری، آپلود Artifact یا نگهداری پس از پایان GitHub Job ایجاد نشده است.

### ۳. کامل‌بودن زنجیره تصمیم

کنترل `verifyTraces()` فقط معتبر بودن هش‌ها را نمی‌سنجد؛ دنباله هر `requestId` را نیز بررسی می‌کند:

- **رد در BFF:** `BFF_PREFLIGHT DENY → BFF_RESPONSE DENY`
- **رد در Nest:** `BFF_PREFLIGHT CANDIDATE → NEST_SCOPE DENY → BFF_RESPONSE DENY`
- **تصمیم PDP:** `BFF_PREFLIGHT CANDIDATE → NEST_SCOPE CANDIDATE → PDP_RESULT DENY/SIMULATED_ONLY → BFF_RESPONSE DENY`

هر پاسخ ساختگی مثبت PDP هم در خروجی BFF بسته می‌ماند. وجود `SIMULATED_ONLY` در لاگ **هیچ اجازه خواندن یا افشای اطلاعاتی ایجاد نمی‌کند**. ناقص بودن مسیر به‌عنوان خطای ممیزی گزارش می‌شود.

### ۴. آزمون‌های قابل تکرار در GitHub

`scripts/ci/w24-durable-audit-ledger.test.cjs` روی دیسک موقت Runner واقعی، ایجاد، `fsync`، بازگشایی، الحاق‌های هم‌زمان، قفل writer، سخت‌گیری فیلدهای مجاز، تغییر رکورد، تغییر checkpoint، حذف دم زنجیره، write ناقص، Symlink swap، نقص مسیر و قطع دسترسی آزمایشی را آزمایش می‌کند.

`scripts/ci/w24-bff-nest-pdp-audit-chain.test.cjs` در یک سرویس HTTP آزمایشی (نه Route واقعی) درخواست سهامداران ساختگی را از BFF → Nest → PDP عبور می‌دهد؛ پس از ثبت هر مرحله، زنجیره را بررسی می‌کند. آزمایش می‌کند که درخواست ناشناس یا غیرمالک پیش از Nest رد شود، مجوز منبع در Nest مستقلاً کنترل شود، Timeout باعث رد شود، پاسخ آلوده افشا نشود، داده محرمانه وارد دفتر نشود و خرابی checkpoint **قبل از ارسال به Nest** منجر به HTTP 503 شود.

`scripts/ci/test_w24_durable_audit_contract.py` صحت معماری و جلوگیری از واردشدن W2.4 به Routeهای عملیاتی، `AppModule`، پرونده داده واقعی یا گیت Docker را کنترل می‌کند.

Workflow صرفاً برای Draft شاخه دقیق `test/w2-4-durable-audit-no-docker-20261101` فعال می‌شود. ضمن Build/TypeScript و آزمون‌های پایه، مجموعه‌های W2، W2.2، W2.3 و W2.4 را اجرا می‌کند؛ شش مرحله Docker/SQL/OCI اجرا نمی‌شوند.

## ۵. معیار پذیرش و خطرات باقیمانده

پذیرش W2.4 فقط بعد از **GitHub Actions SUCCESS روی SHA نهایی**، صفر خطای آزمون، پاس‌بودن تمام نشانگرهای ممیزی و تأیید skipped بودن شش مرحله Docker ممکن است. جزئیات دقیق در قرارداد JSON هم‌نام قرار دارند.

از دید بهره‌برداری، موارد زیر **مسدود و طراحی‌نشده** هستند: ذخیره‌سازی audit چندگره‌ای و قابل اعتماد در تولید، نگهداری و حذف مطابق قوانین حفاظت داده، امضا/مهر زمانی معتبر و WORM، تأیید منابع رسمی، سامانه هویت/مالکیت واقعی، ثبت فیزیکی SQL، RLS، Merge و Deploy، و معاملات و پرداخت.

**این فاز هیچ نوع مجوز عملیاتی سهامداری، انتقال مالکیت یا پرداخت ایجاد نمی‌کند.** منبع کاربر همچنان فقط شفافیت سهامداری است؛ سیستم حسابداری عمومی تعاونی در دامنه پلتفرم نیست.
