# W2.5 — مدیریت نسخه سیاست امنیتی و رد تصمیم‌های منسوخ PDP

**تاریخ:** ۱ نوامبر ۲۰۲۶  
**مبنای پذیرفته‌شده:** W2.4، PR #74، SHA `c3ea5a92b7f0ea48bff986be66b4cac3916d96ad`  
**محدوده:** GitHub Actions، داده و زمان ساختگی، مرجع سیاست درون‌حافظه‌ای، بدون Docker، پایگاه داده، Merge یا انتشار عملیاتی.  
**وضعیت پذیرش:** فقط پس از موفقیت واقعی CI روی SHA نهایی و گزارش مارکرها قابل پذیرش است.

## ۱. مسئله امنیتی

در W2.2 تصمیم PDP قابل لغو شد و W2.3 قرارداد BFF/Nest را در حالت غیرفعال تثبیت کرد. در W2.4 ممیزی چندمرحله‌ای و فایل هش‌دارِ صرفاً آزمایشگاهی اضافه شد. اما هنوز پاسخ مثبت شبیه‌ساز، خودش مشخص نمی‌کرد به کدام نسخه مشخص و معتبر سیاست تعلق دارد. همچنین ممکن بود نسخه سیاست در فاصله بین درخواست PDP و نخستین دسترسی به منبع تغییر کند.

**اصل W2.5:** نتیجه PDP فقط وقتی برای یک *خواندن مصنوعی* قابل بررسی است که نسخه معتبر، تازه، ابطال‌نشده، با اثرانگشت درست و متعلق به همان نسل فعال‌سازی باشد. این اجازه صرفاً `SIMULATED_ALLOW` است و هرگز مجوز افشای اطلاعات یا اجرای عملیات واقعی نیست.

## ۲. مرجع سیاست مستقل و تاریخچه تغییرات

`scripts/security/w25-synthetic-policy-registry.cjs` یک مرجع کاملاً ساختگی در حافظه آزمایش است:

- `policyId` ثابت: `SYNTHETIC_SELF_READ_ONLY`.
- `revision`: عدد صحیح افزایشی؛ شماره قبلی دوباره استفاده نمی‌شود.
- `ruleset`: فقط دو نسخه ساختگی تعریف‌شده، نه سیاست خریدوفروش یا مجوز واقعی.
- `notBeforeMs` و `expiresAtMs`: محدوده اعتبار بر اساس ساعت تزریق‌شده و کنترل‌شده در آزمون؛ شروع شامل، پایان غیرشامل.
- `digest`: SHA-256 محتوای استاندارد شامل هویت سیاست، نسخه، مجموعه قواعد و زمان‌بندی.
- `epoch`: شماره نسل فعال‌سازی که با فعال‌سازی نسخه جدید یا ابطال تغییر می‌کند.
- `lease`: سند تغییرناپذیر درون‌فرایندی، ثبت‌شده در `WeakSet` خود مرجع؛ کپی یا نسخه دستکاری‌شده حتی با محتوای یکسان، سند صادرشده معتبر محسوب نمی‌شود.

انقضا، ابطال، خروج از زمان معتبر، تغییر نسل، تغییر محتوای سیاست یا استفاده از نسخه قدیمی باید `DENY` برگرداند. پس از ابطال، فعال‌سازی دوباره همان نسخه مجاز نیست. این مرجع، اجماع توزیع‌شده یا مخزن سیاست‌های قانونی نیست.

## ۳. اعتبارسنجی نسخه در زنجیره تصمیم

`scripts/security/w25-synthetic-policy-version-enforcer.cjs` فقط نامزد ساخته‌شده توسط قرارداد آزمایشی W2.3 را می‌پذیرد. زنجیره:

```
NextRequest ساختگی در BFF
  → گیت نشست/تعاونی/مالکیت W1
  → نامزد شش‌فیلدی W2.3
  → بررسی مستقل Nest W2.3 (synthetic)
  → مرجع W2.5: صدور lease معتبر و بررسی نسخه
  → PDP Python قابل‌لغو W2.2
  → بررسی مجدد lease و نسخه فعال پس از await
  → بررسی دقیق اثرانگشت، نسخه و epoch پاسخ
  → ثبت ممیزی W2.4 و ردیف نسخه بدون اطلاعات حساس
  → بررسی مجدد نسخه درست پیش از منبع مصنوعی
  → source.read مصنوعی (فقط اگر همه کنترل‌ها پاس شوند)
  → مفسر BFF: همچنان پاسخ 403 یا 503، بدون اجازه/اطلاعات واقعی
```

هر یک از حالات `policy not active`، `not before`، `expired`، `revoked`، `stale`، `digest mismatch`، `epoch mismatch`، `timeout`، `abort`، `invalid response` یا `audit unavailable` باید به رد درخواست **پیش از منبع مصنوعی** منجر شوند. اگر یک منبع قبلاً فراخوانی شده اما خروجی نادرستی داده، شمارنده اقدام باید صادقانه مقدار یک را گزارش کند و BFF اجازه ارسال نتیجه را ندارد.

## ۴. پیوند با ممیزی W2.4

پرونده آزمایشی W2.4 همچنان فقط `requestId,phase,decision,reasonCode` و اطلاعات شماره‌گذاری/هش را می‌نویسد؛ schema پذیرفته‌شده آن تغییر نکرده است. یک دفتر نسخه مجزا **فقط در حافظه همین آزمون**، شش فیلد بی‌هویتِ `requestId,policyRevision,policyDigest,policyEpoch,decision,reasonCode` را به تصمیم متصل می‌کند. هر دو ثبت باید قبل از مراجعه به منبع ساختگی موفق شوند.

این پیوند برای ردیابی نسخه در طول اجرای آزمایش کافی است، **اما هنوز ممیزی پایدار شامل نسخه سیاست نیست**؛ آن قابلیت نیازمند طراحی مجزای schema رسمی، امضا/چک‌پوینت مستقل و محل ذخیره بادوام است.

## ۵. تفاوت «اثر انگشت سیاست» و «گواهی امضاشده PDP»

در این مرحله، Wrapper قابل لغو پس از اجرای شبیه‌ساز W1 Python، metadata نسخه صادرشده توسط مرجع آزمایشی را به پاسخ می‌چسباند. این روش امکان آزمایش تطبیق نسخه، ابطال و رد پاسخ دیرهنگام را فراهم می‌کند، اما **به‌هیچ‌وجه اثبات رمزنگاری‌شده آن نیست که خود PDP دقیقاً همان نسخه سیاست را اجرا کرده است**. برای بهره‌برداری آینده، باید سیاست منتشرشده و پاسخ PDP هر دو با هویت، امضا، شناسه درخواست، نسخه، hash و قواعد دارای اعتبار مستقل قابل راستی‌آزمایی باشند.

همچنین مرجع درون‌حافظه‌ای W2.5 به‌تنهایی تغییر هم‌زمان نسخه بین چند Instance، ری‌استارت فرآیند، تغییر ساعت سیستم یا تأخیر اعلان ابطال را کنترل نمی‌کند.

## ۶. بسته آزمون و CI

`scripts/ci/w25-policy-revision-expiry.test.cjs` باید با یک نسخه معتبر و فرایند واقعی W2.2 Python شروع کند؛ سپس نبود نسخه فعال، اعتبار زمانی، انقضا در انتظار PDP، ابطال حین PDP، جایگزینی نسخه، جعل epoch و digest، کپی lease، rollback، خرابی ممیزی، ابطال پس از Audit، Timeout، پاسخ نادرست، عدم افشای اطلاعات دو مالک ساختگی و خودداری از دسترسی منبع را آزمایش کند.

آزمون `scripts/ci/test_w25_policy_revision_guard.py` مانع import کتابخانه آزمایشی به Routeهای عملیاتی، حذف گیت‌های سابق و اجرای Docker در CI این Draft branch می‌شود.

GitHub Actions علاوه بر آزمون W2.5 باید بر همان SHA تمام آزمون‌های W2، W2.2، W2.3 و W2.4 را اجرا کند؛ Build، TypeScript و کنترل‌های Python نیز الزامی‌اند. شش گام Docker/PostgreSQL/OCI باید `skipped` باشند.

## ۷. کنترل‌های غیرقابل عبور

هیچ مجوز رسمی هیأت‌مدیره یا مرجع قانونی، منبع داده، اطلاعات واقعی سهامدار، RLS، کیف پول، خریدوفروش، پرداخت، حسابداری عمومی یا تسویه به‌واسطه W2.5 فعال نمی‌شود. کتابخانه‌های این مرحله در `scripts/security` هستند، نه در Routeهای Next یا `AppModule` Nest. **هیچ Merge یا Deploy دستی انجام نمی‌شود.**

موفقیت W2.5 فقط «پذیرش فنی آزمایشگاهی نسخه‌بندی و رد تصمیم‌های منسوخ» است؛ **نه تأیید امنیتی محیط تولید یا مجوز عملیاتی**.

**NO DOCKER / NO OPERATIONAL DB / NO REAL SHAREHOLDERS / NO TRADING / NO MERGE / NO MANUAL DEPLOY.**
